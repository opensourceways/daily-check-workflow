## 详细复盘

### 问题背景

921 期间，openEuler-docs 和 openGauss-docs 的 sitemap 在现网暴露多个问题，影响搜索引擎抓取。

### 根因分析

#### 问题 1：atom 环境 robots.txt 中域名错误

**根因：** 已有域名自动替换脚本，未在构建时调用，原因是：1）代码提交时遗漏。2）现网未充分测试，只看了 org 环境

#### 问题 2：文档的 sitemap_index 中出现不可访问项

**根因：** 根据远程 git 仓库分支来拼接多版本 sitemap 地址，不稳定且容易引入不可访问的版本。涉及问题：sitemap index 生成的逻辑未在多个项目间同步

#### 问题 3：hugo 文档 sitemap loc 为相对路径

**根因：** sitemap 由 hugo 自动生成，当前的构建方式（镜像构建时执行 `hugo -b / --minify`（Dockerfile:31），把 baseURL 覆盖成了 `/`）导致生成的 sitemap 的 baseUrl 为 `/`。涉及问题：1）巡查不充分，daily check 自动化巡查未查出 sitemap.xml 元素值的规范性问题

### 规避/修复措施

| 问题 | 规避措施 |
|------|----------|
| robots.txt 域名错误 | 现网已修复，后续定期人工/自动巡查现网 sitemap.xml 内域名是否正确 |
| sitemap_index 不可访问项 | 使用项目内维护的多版本名称列表来拼接多个版本的 sitemap 地址，后续检查多个 Vitepress 项目间的相关逻辑是否同步、定期人工/自动巡查现网 sitemap 地址是否可访问 |
| hugo loc 相对路径 | 定期人工/自动巡查 |

### 后续跟进

- 重构当前的落地措施
- daily check 自动化巡查在 sitemap 方面的扫描能力/覆盖范围不足，且问题通过提 issue 的方式提出，感知度低。优化措施：先在本地创建针对 sitemap 的自动化巡查的脚本，主要检查：
  - loc 地址是否符合规范、能否正常访问
  - lastmod 是否明显不正常（所有页面都一样）
  - changefreq 是否为 never
  - xhtml:link 是否缺失
- 每天/定期人工调用执行，或用操作系统的定时任务执行
