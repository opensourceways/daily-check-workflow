# JSON-LD 检测方式

## 检测项

| 检测项 | 检测方式 | 预期结果 | 自动化 |
|--------|----------|----------|--------|
| JSON-LD 存在 | 解析页面 `script[type="application/ld+json"]` | 首页 + 内容页均有（采样验证） | ✅ 脚本 |
| 注入方式 | 检查 SSG/SSR 输出的原始 HTML | 非客户端动态注入 | 🟡 半自动（查看源代码） |
| JSON 语法 | `JSON.parse` | 无语法错误 | ✅ 脚本 |
| @context | 块级校验（**支持数组形式块 `[{...}]`**） | 固定 `https://schema.org` | ✅ 脚本 |
| 重复块检测 | 同页内 JSON 序列化比对 | 无完全重复的块（模板+插件双重注入是常见根因） | ✅ 脚本 |
| P0 三件套覆盖 | 解析 `@type`（含 `@graph` 展开） | Organization / WebSite / BreadcrumbList 在采样页齐全 | ✅ 脚本 |
| 必填属性完整 | 按 Google 各类型必填属性校验 | 齐全且非空 | ✅ 脚本 |
| 嵌套结构 | BreadcrumbList（position+name）/ FAQPage（acceptedAnswer.text）/ headline ≤110 字符 | 无错误 | ✅ 脚本 |
| 实体关联 | `@id` 覆盖率、`@graph` 使用 | P1：WebPage.isPartOf → WebSite → Organization 引用链完整 | ✅ 脚本（informational） |
| 语言标记 | 页面级节点（WebPage/WebSite/Article）检查 `inLanguage` | `zh-CN` | ✅ 脚本 |
| logo 形态 | Organization.logo | ImageObject 形式且 url 为绝对 URL；缺失/裸字符串/相对 URL 均记为问题 | ✅ 脚本 |
| 占位符 | 递归扫描字符串取值 | 无 TODO/FIXME/待填/占位 | ✅ 脚本 |
| 取值真实 | 对比页面可见内容 | 无编造数据（评分/价格/日期/作者） | ❌ 人工 |
| 富媒体资格 | [Rich Results Test](https://search.google.com/test/rich-results) | 目标类型零错误 | ❌ 人工 |
| 词汇合法性 | [validator.schema.org](https://validator.schema.org/) | 零错误 | ❌ 人工 |
| 本地/CI 门禁 | `skill/scripts/validate-jsonld.mjs --dist <产物>` | 退出码 0 | ✅ skill 脚本 |

## 自动化检查

- 检查脚本：`scripts/checks/check-jsonld.mjs`（package.json 别名 `check:jsonld`，参数与执行流程见 [工具与脚本](工具与脚本.md)）
- 采样策略：首页 + `check-rules.json` 的 `samplePages`（`/docs`、`/zh/docs`）+ 各项目 llms.txt 前 2 条真实内容页链接（.md 转 .html），仅统计返回 200 的页面（采样页 404 不报错；首页不可访问计硬性错误）
- 两种运行模式：
  - 常规检查（默认）：`node scripts/checks/check-jsonld.mjs [--site=ID]`，含全部明细的汇总报告
  - 提 issue 模式：追加 `--submit-issues`（可加 `--dry-run` 只打印正文不提单、`--force` 强制执行写回原 issue），按项目查重→扫描→brief/full 双报告→提单，汇总报告仅保留总览
- 执行方式：GitHub Actions 每日定时（见下文）或 `node scripts/checks/run-all.mjs` / 单独执行
- 输出（均写入报告归档目录 `scheduled-reports/jsonld/<YYYY-MM-DD>/`，目录内文件名不含日期）：
  - `report.md`（总览表 + 各项目明细；提单模式仅总览 + full 指针清单）
  - 提单模式对发现 P0 硬性错误的项目：`<项目ID>-brief.md` / `<项目ID>-full.md`
  - 机器可读：`scripts/stats/jsonld-stats.json`（两种模式都输出）
    - 覆盖：`perPage`（每页块数与类型）、`jsonLdCount`/`invalidCount`、`p0Missing`
    - 合法性：`contextErrors`（@context 异常，支持数组块）、`duplicateBlockCount`/`pagesWithDuplicates`（重复注入）
    - 字段：`requiredMissing`（字段级缺失）、`nestedIssues`（面包屑/FAQ/headline/logo/inLanguage）、`placeholderHits`
    - 关联：`idCoverage`（@id 覆盖率）、`usesGraph`
    - 分级：`hardErrors`（P0）、`warnings`（P1/结构项）、`verdict`（❌/⚠️/✅）

## 提 issue 流程（--submit-issues）

- 逐项目先向 AtomGit 目标仓库查重（标题前缀 `[GEO JSON-LD]`，常量定义于 check-jsonld.mjs，变更会使旧 issue 查重失效），存在未关闭同前缀 issue 则跳过该项目整个"扫描+提单"；查询失败时，有 token 为防重复提单直接跳过，无 token（本地试跑）只扫描不提单。查重与写回为 `scripts/lib/atomgit.mjs` 公共实现（`precheckExistingIssues`/`reconcileIssue`，6 维度一致）
- **强制执行模式（`--force`，对应 workflow 手动输入的 `force_check`）**：修复合并后想立即复核——查重命中不再拦截扫描；仍有 P0 硬性错误 → PATCH 就地更新原 issue 标题与正文（不新建）；硬性错误已消除且首页抓取成功（有效复检）→ 在原 issue 评论 `/close` 自动关闭；抓取失败不下"已修复"结论、不评论
- 触发提单条件：**存在 P0 级硬性错误**（首页不可访问、无合法块、JSON 语法错误、@context 异常、P0 三件套缺失、Google 必填属性缺失、占位符）；P1/结构告警（重复块、面包屑项、headline 超长、logo 形态、inLanguage、@id 覆盖率）仅记入报告供人工定夺，不提单
- 报告形态：双报告（`<ID>-brief.md` 简短版进 issue 正文 + `<ID>-full.md` 完全版挂链），与 TDK 重复/Sitemap/HTML 语义化维度一致
- 固定处理说明：修复后关 issue；issue 未关闭期间（定时检查）不会重复扫描/重复提单；误报（如采样页确实不适用某类型）请评论说明后关闭；维护者手动 force_check 强制复例外会更新或直接评论 /close 关闭
- GitHub Action：`.github/workflows/json-ld-check.yml`（每日 06:00 UTC + workflow_dispatch 支持 `site`/`dry_run`/`force_check`），产物报告 commit 回本仓库 `scheduled-reports/jsonld/<YYYY-MM-DD>/`；cron 仅在默认分支 main 生效

## 人工检查要点

- 查看页面源代码（非 DevTools 元素面板）确认 ld+json 为 SSG/SSR 输出
- AI 生成/脚本生成的取值是否与页面可见内容一致
- 占位符是否在发布前移除
- 面包屑名称是否与页面可见导航一致
- 使用 [Google Rich Results Test](https://search.google.com/test/rich-results) 与 [validator.schema.org](https://validator.schema.org/) 抽查核心页面
